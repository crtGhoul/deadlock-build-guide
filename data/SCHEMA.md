# 3-Archetype Build Schema

One JSON file per hero: `data/archetypes/<hero-slug>.json` (slug = lowercase, spaces→`-`, e.g. `grey-talon`, `deadman-danny`, `mo-krill`).

```json
{
  "hero": "grey-talon",
  "name": "Grey Talon",
  "meta_archetype": "weapon",
  "archetypes": {
    "weapon":   { "...": "see below" },
    "spirit":   { "...": "see below" },
    "vitality": { "...": "see below" }
  }
}
```

## Archetype object

| Field | Type | Rules |
|---|---|---|
| `label` | string | `"Weapon / Gun"`, `"Spirit"`, or `"Vitality / Sustain"` |
| `is_meta` | bool | Exactly one archetype `true`; must match `meta_archetype` |
| `tagline` | string | One-line pitch for the playstyle |
| `kit_synergy` | string | How THIS hero's abilities enable THIS archetype (name the abilities; imbue targets for spirit) |
| `skill_order.unlock` | string[4] | Ability unlock order (use exact names from `scripts/ability-names.json`) |
| `skill_order.max_priority` | `{"1":…, "2":…, "5":…}` | Which ability to max at 1/2/5 AP, with a one-line why |
| `skill_order.track` | string[16] | Full 16-step skill-up track (ability names, may repeat) |
| `phases.p1.items` | `[{name, why}]` | 4–6 items. **Primary-category spend must total exactly 4800.** |
| `phases.p1.spike` | string | e.g. `"4800 Weapon — +49% weapon damage spike"` |
| `phases.p2.items` | `[{name, why}]` | 3–8 core mid-game items |
| `phases.p3.final_loadout` | string[12] | Exact 12 endgame items, unique, **≤4 actives** |
| `phases.p3.sell_upgrade` | `[{from, to, why}]` | Which early items are sold vs upgraded into T3/T4 |
| `phases.p3.win_condition` | string | How the hero wins past 30k souls |
| `counters.vs_danny` | string | Danny-specific counter play for this archetype |
| `counters.vs_baba` | string | Baba-specific counter play |
| `counters.vs_violet` | string | Violet-specific counter play |
| `counters.swaps` | `[{vs, out, in, why}]` | ≥3 one-for-one item swaps |

## Shop rules (enforced by `scripts/validate-archetypes.py`)

- Item names MUST exist in `scripts/itemdb.json` (live Deadlock API snapshot, Oct 2026). Costs are pulled from the DB — never invent prices.
- Tiers: 800 / 1600 / 3200 / 6400 only. Categories: Weapon / Vitality / Spirit (`itemdb.json`).
- Final loadout: exactly 12 unique items, max 4 with `active: true` (Z/X/C/V slots).
- Component chains in `scripts/components.json` — prefer early buys that upgrade into late T3/T4 (validator warns on wasted-soul paths).
- 4.8k spike bonuses (Deadlock wiki, community term "4.8k spike"): Weapon +49% dmg / Vitality +34% HP / Spirit +38 power at 4800 single-category spend.

## NUKE block (`archetypes.nuke`, added 2026-10-22)

A 4th build path per hero: a signature-ability supercharge ("imbue template").
Same phase/skill-order/shop rules as the 3 archetypes, plus:

| Field | Type | Meaning |
|---|---|---|
| `primary_category` | `"Spirit"` or `"Weapon"` | Category the p1 4,800 spike is measured in (Weapon only for Rat King — Scrap Grenade scales with weapon damage) |
| `best_ability.name` | string | The chosen signature ability (exact name from `ability-names.json`) |
| `best_ability.scaling` | string | Base damage + spirit scaling figure, sourced (deadlock.wiki preferred; the API scaling file misattributes some properties) |
| `best_ability.why` | string | Why this ability is the pick |
| `best_ability.alternates` | `[{name, when}]` (≤2) | Other imbue candidates and when to pick them |
| `imbue_stack` | string[] | Ordered imbue items assigned to the signature ability |
| `damage_math` | string (optional) | Deep-dive heroes only: computed per-cast damage at the final loadout's Spirit Power, inputs shown |
| `cooldown_build` | bool (optional) | True when the hero has no real damage nuke (Haze, Wraith, Mirage, Vindicta, Nurse Harrow) — copy must say so plainly |

`is_meta` is always false for NUKE (META stays one of the 3 archetypes), and its
`counters` carries only `swaps` (≥3) — the validator enforces all of this.
Generated by `scripts/gen-nuke.py`; payload name is `<Hero> - Nuke`.

## CN block (`archetypes.cn`, added 2026-11-03)

A 5th build path per hero: a Chinese-community tempo build. Same
phase/skill-order/shop rules as the other archetypes, plus:

| Field | Type | Meaning |
|---|---|---|
| `primary_category` | `"Spirit"`, `"Weapon"`, or `"Vitality"` | Category the p1 4,800 spike is measured in (declared per hero; the CN lean may differ from META) |
| `cn_note` | string | What is distinctly Chinese about the build — item choices, tempo, lane/jungle style. Must read like it came from the CN meta, not generic filler |
| `cn_source` | string | Source type + URL where a stable Chinese-language guide page exists (deadlock.coach/zh-CN, deadlockdb.wiki/zh, worldlock.org/zh-cn, games.gg/zh-CN/zh-Hant, metabot.gg/zh_CN, deadlocklabs.gg/zh); otherwise the honest consensus label: "CN meta consensus — no single pro source found (Chinese community build library: https://deadlockdb.wiki/zh/builds/)" — never a made-up pro attribution |

`is_meta` is always false for CN (META stays one of the 3 archetypes), and
its `counters` carries the FULL module (vs_danny/vs_baba/vs_violet + ≥3
swaps) — the validator enforces all of this. Tab order is Weapon, Spirit,
Vitality, NUKE, CN; META stays the default tab everywhere, never CN; deep
link is `?build=cn`. Generated by `scripts/gen-cn.py` (CN-ifies the
same-lean build: same skill order, CN core swapped into the phases, CN
final differing from META final by ≥4 items); payload name is
`<Hero> - CN`.

## Situational counter-buys (`situational`, added 2026-10-23)

Every archetype object (all 4 paths, NUKE included) carries a `situational`
array of 5–7 conditional rules — the "in case this, buy that" system —
generated by `scripts/gen-counterbuys.py` from a damage-type/hero-trait
rule table. Never hand-edit; fix the generator's table and regenerate.

| Field | Type | Rules |
|---|---|---|
| `when` | string | Short game-state condition ("Lifesteal / heal comp — they out-sustain every trade") |
| `buy` | string | Real buyable item from `itemdb.json`; tuned to the build's damage type |
| `sell` | string \| null | A flex item from the build's final 12 to give up. Distinct per build; never the build's core, never a NUKE imbue-stack item, never a component of `buy`. `null` = the owned variant below |
| `note` | string | One line of concrete mechanic (real numbers from the item's API data) |

Owned variant: when the natural counter item is already in the final 12,
`buy` names it, `sell` is `null`, and `note` ends with "Already in this
build — buy it a phase earlier instead of waiting for the full build."
(Vitality builds fall through to a fresh same-class defensive swap instead
when one exists — their finals pre-slot most defensive answers.)

House rule: after any swap the final 12 still has ≤4 actives (if `buy` is
active, `sell` is an active or the build's final actives were ≤3). The
validator enforces count, membership, distinct sells, the owned-variant
shape, and the active cap; `verify_integrity.py` enforces tooltip coverage
for every `buy`.

On site: the "⚔ Counter-buys — if the game looks like this" panel
(`archSituationalHtml`) renders each rule with a tooltip-wired buy chip +
soul cost. Both text exports include the rules: the full guide renders
"IF <when> -> BUY <item> (<cost>) instead of <sell> — <note>", the compact
shopping list renders them as one-liners.

## AP economy model (`scripts/ap-model.json`, added 2026-10-23 — Prompt 31)

Generated by `scripts/gen-ap-model.py` from the game's own data
(`api.deadlock-api.com/v1/assets/heroes` `level_info`, cross-checked against
deadlock.wiki/Boons — the two agree exactly) — never hand-edit; fix the
generator. Fields: `levels[36]` `{level, souls, reward}` (souls = total
gathered; level 1 is the 600-soul start and grants an unlock),
`unlock_souls` `[600, 1100, 2000, 3800]`, `total_ap` 32, `tier_costs`
`[1, 2, 5]`, `tier_at_ap` `[1, 3, 8]` (cumulative AP in one ability at which
tiers 1/2/3 complete), `ultimates` `{hero: ability}` (from each hero's
`signature4` item class in the API), `assumptions[]`.

Validator (`check_ap_model` in `scripts/validate-archetypes.py`) reading: a
16-step track is a chronological spend sequence — first step on an ability is
its unlock, later steps are +1 AP each; saving is legal, so funding is the
greedy earliest simulation. Hard errors: names outside the hero's ability
set, >8 AP into one ability, unfundable sequences. Warnings (reported, never
silently fixed): the ultimate taken before the 4th unlock, `unlock[]` not
ending with the ultimate, track/`unlock[]` order drift. As of 2026-10-23 the
shipped data carries 68 ultimate-timing warnings across 176 builds — the
authored tracks read partly as priority order; the on-site simulator enforces
the real rules for custom orders and defers early ultimate steps when loading
a recommended track (same 16 spends, legal order, note shown).

`build-site.py` exports a compact copy as `window.AP_MODEL`
(`levels: [[souls, 'U'|'A']…], tierCosts, tierAt, ults, totalAp`) for the
simulator in `assets-src/arch-ui.js`.

## Build Creator share links (`?b=`, added 2026-10-23 — Prompt 33)

Payload JSON `{v: 1, h: <hero slug>, n: <build name>, i: [<item name>…]}`,
UTF-8 → Base64url, carried in `?b=` on the guide URL. Import is fail-closed
(`parseSharePayload` in `assets-src/arch-ui.js`): the raw value must match
the Base64url alphabet and decode to ≤ 4 KB; JSON.parse inside try/catch;
only the keys `v/h/n/i` are read (any other key — `__proto__`,
`constructor`, anything — rejects the whole import); `v` must be 1; `h` must
be one of the 44 hero slugs; `i` must be an array of ≤ 12 unique strings,
each exactly naming a buyable shop item in `scripts/itemdb.json`; `n` is a
string, truncated to 60 chars, and only ever rendered as text (input value /
textContent — never innerHTML). Any failure opens the creator empty with a
"that share link wasn't valid" notice; nothing is partially applied.

Exact per-hero ability names live in `scripts/ability-names.json` — copy them verbatim.

## Item tooltips (`scripts/itemtooltips.json`, added 2026-10-22 — Prompt 32)

Generated by `scripts/gen-itemtooltips.py` from the live API
(`https://api.deadlock-api.com/v1/assets/items`) — never hand-edit; fix the
generator. Coverage = itemdb.json's buyable set (cost ∈ {800,1600,3200,6400},
no `upgrade_` prefix). One entry per item name:

| Field | Type | Source / rules |
|---|---|---|
| `cost` | int | Souls; cross-checked API == itemdb |
| `tier` | 1–4 | Derived from cost (800→1 … 6400→4) |
| `cat` | string | Weapon / Vitality / Spirit (itemdb; cross-checked vs API slot) |
| `active` | bool | Resolved API record's `is_active_item` (duplicate names: prefer type=upgrade, cost match, then `shopable` — e.g. Silencer resolves to the live passive `upgrade_proc_silence`, NOT itemdb's stale active flag) |
| `cd` | number | Actives only: `AbilityCooldown` seconds. Absent for passives and for toggle/one-shot actives whose API cooldown is 0 (Blood Tribute, Golden Goose Egg) |
| `imbue` | bool | API record's `imbue` marker |
| `fx` | string[] | Effect lines: section `loc_string`s in tooltip_sections order (deduped), description first only when it isn't one of them. Tags/SVG stripped |
| `stats` | string[] | Bonus lines from the API's own `tooltip_sections` display manifest: per attribute elevated → important → plain properties, sections in API order, deduped, formatted as the shop prints them (`+20% Weapon Damage`, `15m Close Range`). Skipped: zero values, label-less/internal properties, `StatusEffect*` refs, and `AbilityCooldown` (surfaced via `cd`) |

Known divergence: Silencer gains a `1.04% Buildup Per Shot` line from the API
manifest that the deadlock.wiki infobox omits (it covers buildup in a Notes
section). The generator follows the API uniformly — no per-item exceptions.

`build-site.py` exports this as `window.ITEM_TOOLTIPS` in
`assets/data/archetypes.js` with short keys to stay lean:
`c`=cost, `t`=tier, `g`=cat, `a`=active(1), `d`=cd, `i`=imbue(1), `f`=fx, `s`=stats
(optional keys omitted when empty). The delegated tooltip UI
(`assets-src/arch-ui.js`) renders any element carrying `data-item-tip="<Item Name>"`;
items missing from the dataset fall back to name+cost/category from
`ARCHETYPE_ITEMDB`, so a tooltip is never empty. `verify_integrity.py`
enforces 100% tooltip coverage for every item referenced by any build.
